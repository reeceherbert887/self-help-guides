# Important Thing I Learned

I do **not** need to install WireGuard on TrueNAS, Home Assistant, or every internal server.

WireGuard only needs to be installed on:

- OPNsense as the VPN server
- Devices I want to connect **from**, for example:
  - Phone
  - Linux laptop
  - Tablet
  - Work laptop if needed

So the idea is:

```text
Phone / Laptop
   |
WireGuard VPN
   |
OPNsense
   |
Home Network
   |--- TrueNAS
   |--- Home Assistant
   |--- Desktop
   |--- Other devices
```

For a new remote device, I only add a new WireGuard peer.

Example:

| Device | WireGuard VPN IP |
|---|---:|
| Phone | `Your IP` |
| Linux Laptop | `Your IP` |
| Tablet | `Your IP` |

## Peer Section

| Setting | Value |
|---|---|
| Public Key | `CfJR0YMy6LQt5L5tqKMW+jXZvGWcNcuZZWZcJnztOAo=` |
| Pre-shared Key | Blank |
| Allowed IPs | `0.0.0.0/0` |
| Endpoint | `77.86.119.50:51820` |
| Persistent Keepalive | `25` |

This was one of the biggest mistakes during the setup:

I accidentally put the phone's own public key into the phone's **Peer Public Key** field.

That is wrong.

The phone's **Peer Public Key** must be the OPNsense server public key.

So:

```text
Phone Interface Public Key
    goes into
OPNsense Peer Public Key
```

and:

```text
OPNsense Instance Public Key
    goes into
Phone Peer Public Key
```

# Eero Port Forwarding

Because OPNsense is currently behind the Eero, the Eero had to forward UDP 51820 to OPNsense.

In the Eero app, the port forward needed to be:

| Setting | Value |
|---|---|
| Device | OPNsense |
| IP | `Your IP` |
| External Port | `51820` |
| Internal Port | `51820` |
| Protocol | UDP |

This is required because the internet hits the Eero first.

Without this port forward, the phone would send traffic but OPNsense would never see it.

# OPNsense Firewall Rules

## WAN Rule for WireGuard

Location:

```text
Firewall → Rules → WAN
```

Required rule:

| Setting | Value |
|---|---|
| Action | Pass |
| Interface | WAN |
| Direction | In |
| TCP/IP Version | IPv4 |
| Protocol | UDP |
| Source | Any |
| Destination | WAN Address |
| Destination Port | `51820` |
| Description | `Allow WireGuard` |

This allows WireGuard traffic from the internet into OPNsense.

## WireGuard Interface Rule

Location:

```text
Firewall → Rules → WireGuardServer
```

Required rule:

| Setting | Value |
|---|---|
| Action | Pass |
| Interface | WireGuardServer |
| Direction | In |
| Protocol | Any |
| Source | Any |
| Destination | Any |
| Description | `Allow WireGuard` |

This allows traffic coming through the VPN tunnel.

For a more secure setup later, this can be restricted, but for testing it was easiest to allow all.

# Interface Assignment Issue

This was another major problem.

At one point, I had created an interface called WireGuard, but it was assigned to:

```text
igb0
```

That was wrong because `igb0` is a physical NIC, not the WireGuard tunnel.

The correct WireGuard interface must use:

```text
wg0 (WireGuard - WireGuard-Server)
```

Correct setup:

```text
Interfaces → Assignments
```

| Interface | Device |
|---|---|
| LAN | `igb2` |
| WAN | `igb3` |
| WireGuardServer | `wg0 (WireGuard - WireGuard-Server)` |

After assigning `wg0`, I had to save/apply.

# What Went Wrong

## 1. Wrong Peer Key

At one point, OPNsense had an old phone public key:

```text
kNveeie/HqwwRu39gTC7l0KHDnkIrVUHde8KbpygilQ=
```

but the phone had a different key.

This caused:

```text
Phone TX increasing
Phone RX = 0
OPNsense handshake blank
```

Fix:

- Delete duplicate/old peers
- Create one clean peer
- Put the current phone public key into OPNsense

## 2. Multiple Duplicate Peers

There were two `Reece-Phone` peers in OPNsense.

That made everything confusing.

Fix:

- Delete old duplicate peers
- Keep one clean peer only

## 3. Pre-shared Key Mismatch

OPNsense had a pre-shared key generated, but the phone did not have that same key.

A PSK mismatch can break the handshake.

Fix:

- Leave Pre-shared Key blank on both sides

Final setup:

```text
Pre-shared key = blank
```

on both OPNsense and phone.

## 4. Phone Peer Public Key Was Wrong

On the phone, I accidentally put the phone's own public key into the Peer Public Key field.

Wrong:

```text
Phone Peer Public Key = Phone Public Key
```

Correct:

```text
Phone Peer Public Key = OPNsense Server Public Key
```

## 5. WireGuard Interface Assigned to Physical NIC

The interface was accidentally assigned to:

```text
igb0
```

instead of:

```text
wg0
```

Fix:

```text
Interfaces → Assignments → WireGuardServer → wg0
```

## 6. The GUI Did Not Show Everything Clearly

The OPNsense GUI status was confusing because sometimes it showed sent/received bytes but no clear reason why the handshake failed.

The actual useful commands were:

```sh
wg show
```

and:

```sh
tcpdump -ni igb3 udp port 51820
```

# Useful Diagnostic Commands

## Show WireGuard Status

On OPNsense shell:

```sh
wg show
```

Working output should show something like:

```text
latest handshake: 5 seconds ago
transfer: 38.94 KiB received, 56.59 KiB sent
```

If it shows:

```text
transfer: 0 B received
```

then the handshake is not working.

## Check if WireGuard Packets Reach OPNsense

On OPNsense shell:

```sh
tcpdump -ni igb3 udp port 51820
```

Then turn on WireGuard on the phone using mobile data.

Working packet capture showed packets like:

```text
82.132.237.94.xxxxx > Your IP.51820: UDP
```

This proved:

- Phone was sending traffic
- Eero port forwarding was working
- OPNsense was receiving UDP 51820

## Check OPNsense Interfaces

```sh
ifconfig
```

Useful results:

```text
igb2 = LAN = 192.168.1.1
igb3 = WAN = 192.168.4.56
wg0 = WireGuardServer = 10.10.10.1
```

## Check OpenSSH Status

On OPNsense, the service name is:

```sh
openssh
```

not:

```sh
sshd
```

Correct command:

```sh
service openssh status
```

Working output:

```text
openssh is running as pid XXXXX
```

If needed:

```sh
service openssh start
```

# SSH Setup

## Enable SSH in OPNsense GUI

Location:

```text
System → Settings → Administration
```

Settings used:

| Setting | Value |
|---|---|
| Enable Secure Shell | Enabled |
| Permit root user login | Enabled |
| Permit password login | Enabled |
| SSH Port | `22` |
| Listen Interfaces | `All (recommended)` |

Then Save.

## Check SSH from OPNsense Shell

```sh
service openssh status
```

It returned:

```text
openssh is running as PID 42825
```

So SSH was running.

## SSH From Linux Desktop

Because my desktop is on the Eero network, I connected to the OPNsense WAN IP:

```bash
ssh root@192.168.4.56
```

This worked after adding the firewall rule.

## Temporary WAN SSH Rule

Location:

```text
Firewall → Rules → WAN
```

Rule used:

| Setting | Value |
|---|---|
| Action | Pass |
| Interface | WAN |
| Direction | In |
| TCP/IP Version | IPv4 |
| Protocol | TCP |
| Source | `192.168.4.57` |
| Destination | WAN Address |
| Destination Port | SSH / `22` |
| Description | `Allow SSH` |

This allowed my Linux desktop to SSH into OPNsense.

Final proof:

The terminal showed the OPNsense console menu inside the SSH session:

```text
*** OPNsense.local: OPNsense 26.1.6_2 (amd64) ***

LAN (igb2) -> 192.168.1.1/24
WAN (igb3) -> 192.168.4.56/22
WireGuardServer (wg0) -> 10.10.10.1/24
```

So SSH worked.

# Important Security Note

The SSH WAN rule is useful for testing, but long term I should not leave broad WAN management access enabled.

A better long-term setup is:

- Disable SSH access from WAN
- Only allow SSH from:
  - LAN network
  - WireGuard network `10.10.10.0/24`
  - Or my trusted desktop IP only

Since WireGuard now works, the cleaner method is:

1. Connect to WireGuard first
2. SSH into OPNsense through the VPN
3. Avoid exposing SSH on the WAN side

Example future rule:

```text
Interface: WireGuardServer
Protocol: TCP
Source: 10.10.10.0/24
Destination: This Firewall
Port: 22
```

Then SSH to:

```bash
ssh root@10.10.10.1
```

# Adding Another Device Later

If I want to add my Linux laptop later, I do **not** rebuild the server.

I only add another peer.

Example:

## Linux Laptop VPN IP

```text
10.10.10.3/32
```

## OPNsense Peer

```text
Name: Linux-Laptop
Public Key: laptop public key
Allowed IPs: 10.10.10.3/32
Keepalive: 25
Instance: WireGuard-Server
Pre-shared key: blank
```

## Laptop Config

```ini
[Interface]
PrivateKey = <laptop private key>
Address = 10.10.10.3/32
DNS = 1.1.1.1

[Peer]
PublicKey = CfJR0YMy6LQt5L5tqKMW+jXZvGWcNcuZZWZcJnztOAo=
Endpoint = 77.86.119.50:51820
AllowedIPs = 0.0.0.0/0
PersistentKeepalive = 25
```

Each new device needs:

- Its own keypair
- Its own OPNsense peer
- Its own unique VPN IP

But I do **not** need to:

- Create a new WireGuard server
- Create a new port forward
- Create a new WAN rule
- Reassign interfaces again

# What I Would Do Differently Next Time

1. Do not keep deleting and regenerating keys unless absolutely needed.
2. Only have one peer per device.
3. Do not use pre-shared keys until the basic tunnel works.
4. Always compare:
   - Phone public key → OPNsense peer public key
   - OPNsense public key → phone peer public key
5. Use `tcpdump` earlier.
6. Use `wg show` earlier.
7. Do not trust the GUI alone.
8. Make sure WireGuard interface is assigned to `wg0`, not a physical NIC.
9. Remember OPNsense is behind Eero, so Eero port forwarding is required.
10. Once working, lock down WAN access and manage through WireGuard instead.

# Quick Troubleshooting Table

| Symptom | Likely Cause | Fix |
|---|---|---|
| Phone TX increases, RX stays 0 | No handshake | Check keys, PSK, endpoint |
| OPNsense receives 0 B in `wg show` | Packets not accepted | Key mismatch or PSK mismatch |
| `tcpdump` shows packets on 51820 | Network path works | Focus on WireGuard config |
| No packets in `tcpdump` | Eero/port forward issue | Check UDP 51820 forward |
| GUI says peer red cross | No active handshake | Check `wg show` |
| SSH hangs | WAN firewall blocking SSH | Add TCP 22 rule from trusted IP |
| `service sshd status` fails | Wrong service name | Use `service openssh status` |
| Interface assigned to `igb0` | Wrong interface assignment | Assign to `wg0` |
| Multiple Reece-Phone peers | Duplicate peer mess | Delete duplicates and create one clean peer |
